# Cache-Aware Weight Layout: Research Report

Working name: `cache-aware-weight-layout`. Date: 2026-08-27. Companion to `cache-aware-training.md` (same repo grounding: unsloth fast paths, Studio's pinned llama.cpp/GGUF serving path). Status: research only, no product code.

> **Correction (2026-08-28):** §1(iv)'s "no per-expert reader exists" verdict is **llama.cpp-specific**. Colibrì (github.com/JustVugg/colibri) is a counterexample — a runtime that demand-streams individual MoE experts from disk through an evicting per-layer LRU cache. See `colibri-weight-side-optimization.md` for the analysis on that runtime.

## Summary

Permuting weights so co-used parts sit together is output-preserving by construction and nearly free to apply — but a permutation changes *which bytes are adjacent*, never *how many bytes are read*, so it can only pay where the runtime reads a **subset** of the weights non-uniformly. For Studio's dominant case (dense model, fully resident, single user), every locality variant evaluates to approximately zero: dense decode streams every weight every token; prefill GEMMs tile in their own order; mmap paging under pressure needs all pages per token regardless of order; llama.cpp has no per-expert placement (`--n-cpu-moe` moves whole fused per-layer expert tensors, and each expert slice is already contiguous and ~100x larger than a page); and mainline llama.cpp has no contextual-sparsity runtime at all (PowerInfer had to fork it), so neuron reordering has no consumer. Apple's own LLM-in-a-flash paper additionally reports that co-activation *clustering* failed in their hands — hot neurons landed in most bundles and were loaded redundantly — and they shipped simple row-column bundling instead. **The variant that survives, and is arguably better than anything in the first report, is the quantization-grouping permutation**: GGUF k-quants share scales over contiguous 32/256-element blocks along each tensor's input axis, so permuting the MLP intermediate dimension (and optionally the global hidden dimension) to group similar-magnitude channels into the same blocks reduces quantization error at identical bit-width, identical file size, and **zero llama.cpp changes** — the payoff is fidelity (a Q4 closer to the fp16 teacher), which is exactly the original "keep the existing output" constraint. RPTQ and PermuQuant establish the mechanism in adjacent settings; for GGUF k-quants specifically it is **unmeasured**, which makes it a cheap, high-information experiment. Recommended first slice: a permute-then-quantize experiment script graded by the fidelity harness proposed in the first report (that harness is the referee here too — another argument for building it first). Honest caveat up front: k-quants' fine sub-blocks, 6-bit sub-scales, and imatrix weighting already absorb much of the range variance, so the win may be small and concentrated in coarse/low-bit formats (Q4_0, Q4_K, IQ*); the experiment's job is to find out and be willing to report zero.

## 1. The precondition, stated honestly and first

A permutation is a bijection on indices. Total bytes, total FLOPs, and per-tensor access counts are invariant. It can therefore only change performance where reads are **partial** or **non-uniform** (page granularity, cache-line granularity, offload-block granularity). Regime by regime, for this repo's serving path:

**(i) Dense model, fully resident, decode: ~zero, confirmed.** Every decode step streams every weight tensor exactly once (first report's arithmetic: 8B @ Q4_K_M ≈ 4.9 GB/token of weight traffic; bandwidth-bound at 100–550 GB/s on Apple Silicon). Each matmul reads its quantized rows contiguously in whatever order they are stored; there is no subset, so there is nothing for adjacency to improve. DRAM/SLC burst efficiency is already maximal for contiguous row reads. Reordering buys ~0.00 tok/s here. This is Studio's dominant configuration (fit logic refuses loads that don't fit; single user; dense 4B–32B models).

**(ii) Prefill / batched compute: irrelevant.** Prefill is compute-bound; BLAS/Metal/ggml kernels tile the GEMM and choose their own access order over the *whole* matrix. A baked-in permutation trivially "survives" tiling (the kernel neither knows nor cares that rows were renamed), but since all blocks are read regardless, order is performance-neutral. The only order that matters is the storage-layout order *within* rows, which quant formats already fix.

**(iii) mmap paging under memory pressure: ~zero for dense models.** macOS pages are 16 KiB. An 8B Q4_K_M down_proj (4096x14336) is ~33 MB ≈ 2,000 pages; the whole model ~300k pages. Dense decode touches **every** page of every tensor each token, so if the model exceeds RAM the OS must re-fault the shortfall every token — the bottleneck is SSD bandwidth times *total* bytes missing, and no ordering reduces pages-touched. GGUF is already laid out layer-by-layer in execution order, so the fault pattern is already sequential/prefetch-friendly. Reordering *within* tensors cannot help; the model-doesn't-fit case is unusable at any order and Studio's fit logic (`studio/backend/core/inference/llama_cpp.py` offload estimation) exists to avoid it. Page-in order matters for *load time* only marginally (first-touch is sequential either way).

**(iv) MoE with partial offload: the strongest case in theory, no reader in this runtime.** llama.cpp's `--n-cpu-moe N` (Studio exposes it: `LoadRequest.n_cpu_moe`, `llama_cpp.py:173,2206,4738`) keeps the **first N layers' expert tensors** on CPU — per *layer*, all-or-nothing, because each layer's experts are fused into single 3D tensors (`ffn_{gate,up,down}_exps`, experts on the outermost dimension). Consequences: (a) there is no per-expert placement to inform — `--override-tensor` regexes match tensor names and cannot split a fused tensor; (b) at compute time `mul_mat_id` reads only the routed experts' slices, but each expert slice is already contiguous — e.g. Qwen3-30B-A3B (128 experts/layer, 8 active, n_embd 2048, expert FFN 768): ~2.6 MB per expert per layer at ~4.5 bpw ≈ 160 pages. Expert *adjacency* is irrelevant at that size; grouping "hot" experts together changes neither pages touched nor CPU→GPU transfer volume. What would consume expert ordering/placement is a per-expert cache with prefetch (MoE-Infinity class systems, §3) — a server architecture this repo does not ship. Verdict today: ~zero.

**(v) Contextual sparsity: no consumer exists in this serving path.** Mainline llama.cpp does not predict-and-skip MLP neurons — verified: the PowerInfer results were raised as llama.cpp issue #4559 and never merged; PowerInfer is a llama.cpp *fork* with DejaVu-style predictors, neuron-aware sparse operators, and hot/cold GPU/CPU neuron placement. Additionally, modern SiLU/SwiGLU models are not activation-sparse enough to exploit without a relufication finetune (§3). So neuron co-activation reordering has **no reader**: the transform would be baked into a file no shipped runtime reads selectively.

**Ranking of available win on the Studio target: (iv) ≈ (v) ≈ (iii) ≈ (ii) ≈ (i) ≈ 0.** That is the honest headline for the locality half of this idea. The half that survives does not depend on locality at all (§4).

## 2. The permutation algebra

What is exactly output-preserving (in exact arithmetic), and what must move in lockstep. HF orientation used below; note `convert_hf_to_gguf` already permutes Q/K weights between HF and GGUF RoPE conventions, so all surgery should happen in HF space before export.

- **MLP intermediate dim (per layer, independent):** permutation P applied to `gate_proj` rows, `up_proj` rows, and `down_proj` columns simultaneously. `down(P^T) . act(gate(P) x . up(P) x)` = identity on the function. This is the workhorse axis: in GGUF, `ffn_down` stores the intermediate dim as its contiguous ne[0] axis, which is exactly the axis k-quant blocks run along (§4).
- **Attention heads:** whole Q heads may be permuted *within a KV group* together with the matching `o_proj` input-column blocks. Permuting KV heads moves each KV head's k/v blocks plus its entire query group plus the group's o_proj blocks. RoPE is applied identically per head, so head order is RoPE-safe. **Within-head_dim permutation is not allowed**: RoPE rotates fixed dimension pairs (HF rotate-half pairs (i, i+d/2); GGUF/NeoX conventions differ but are equally positional), so permuting inside head_dim changes the function. Confirmed as the prompt suspected.
- **MoE expert order (per layer):** experts are gathered by router index and summed; permute the expert slices and the router `gate_inp` rows (plus any per-expert bias, e.g. DeepSeek's e_score_correction_bias) together — identity.
- **Global hidden dim (one permutation for the whole model):** the residual stream ties every layer to the *same* hidden order, but a single global permutation of n_embd is function-preserving: embedding columns, every projection's input rows/output columns as appropriate, all norm weights (elementwise), all biases. This axis matters because `gate/up/q/k/v` and `lm_head` quantize their blocks along n_embd (§4). Per-layer hidden permutations are impossible — the residual addition fixes one order.
- **Vocab / token-id order:** permute embedding rows, lm_head rows, and the tokenizer id space (GGUF `tokenizer.ggml.tokens` array order, every id-valued metadata field — BOS/EOS/pad, added-token ids; BPE merges are string-based and survive). Expressible in GGUF, output-identical up to logit reindexing, and — uniquely — touches **no reduction axis** (embedding is a row lookup; each logit row is independent), so it is *bit*-identical. But worthless: the embedding lookup reads one ~8 KB row per token (locality already perfect) and lm_head is read in full every decode step. Dead on arrival; documented so nobody tries.
- **Layers: cannot be reordered.** The residual stream composes layers sequentially; f_2(f_1(x)) != f_1(f_2(x)). Stated so nobody tries.

**The floating-point caveat.** Permutations that reorder a *reduction* axis change summation order: the MLP intermediate permutation reorders `down_proj`'s contraction; head permutation reorders `o_proj`'s contraction over concatenated heads; the global hidden permutation reorders **every** matmul's contraction; expert permutation reorders the routed weighted sum. ggml accumulates dot products in fp32; reassociation error for a 14k-term fp32 accumulation is ~1e-7..1e-6 relative — four to five orders of magnitude below 4-bit quantization error (~1e-2 relative per weight). Two consequences: (a) logits move by amounts far below quant noise, but greedy argmax can still flip on near-ties, so over long generations occasional token divergence is possible — the same class and magnitude of nondeterminism llama.cpp already exhibits when the thread count or batch size changes summation order, i.e. bit-identity was never on offer from the baseline runtime anyway; (b) only the vocab permutation is truly bit-identical. "Output-preserving by construction" should be stated as: *distribution-identical in exact arithmetic; indistinguishable-from-baseline-nondeterminism in floating point.* One more practical rule: permute in fp16/fp32 **before** quantizing. Permuting an already-quantized tensor along its block axis (e.g. down_proj's ne[0]) crosses block boundaries and forces requantization error; permuting along row axes (gate/up rows, experts, heads) moves whole quant rows losslessly.

## 3. Prior art

- **LLM in a flash** (Apple, arXiv 2312.11514, Dec 2023) [1]: flash/SSD-resident weights, DRAM-limited. Two mechanisms: *windowing* (reuse recently-activated neurons' loaded weights) and **row-column bundling** — store neuron i's up_proj column and down_proj row adjacently so one flash read fetches both. This is the closest existing thing to the proposed idea. Reported: models up to 2x DRAM, **4–5x (CPU) / 20–25x (GPU) speedup over naive flash loading** — i.e. over a *flash-thrashing baseline*, not over a resident model. Critically, they evaluated co-activation *clustering* ("closest friend" bundling) and report it **failed**: hot neurons appear in nearly every bundle and get loaded redundantly, so they shipped the simple per-neuron bundling instead. Also note the precondition: OPT/Falcon-relufied models with ~90%+ activation sparsity and a low-rank activation predictor — none of which llama.cpp has.
- **PowerInfer** (SJTU-IPADS, arXiv 2312.12456, SOSP'24) [2]: hot/cold neuron partition by activation frequency — hot neurons preloaded on GPU, cold computed on CPU, DejaVu-style per-layer predictors, custom neuron-aware sparse kernels. Up to **11.69x over llama.cpp** (OPT/Falcon/relufied models, RTX 4090). It is a **fork**; the ablation shows most of the win needs the predictors + sparse operators + hybrid engine, not the layout alone. Mainline llama.cpp declined to absorb it (issue #4559) [3]. PowerInfer-2 (arXiv 2406.06282) extends to smartphones. Requires ReLU-sparse checkpoints (their Bamboo/TurboSparse models).
- **DejaVu** (arXiv 2310.17157, ICML 2023) [4]: the predictor side — per-input lookahead predictors choose which heads/neurons to compute; up to ~2x over FasterTransformer at no quality loss, but on OPT (ReLU) models and with custom kernels. Establishes that contextual sparsity is real and predictable; also establishes that exploiting it is a *runtime* feature, not a file-layout feature.
- **Co-activation clustering as graph partitioning** (METIS/spectral on a neuron co-activation graph): I could not verify any published work where graph-partitioned neuron clustering beat frequency-based ordering for LLM inference; the one direct data point (LLM in a flash's clustering ablation) is negative. Flagged as unverified-to-exist rather than cited.
- **MoE expert placement/caching**: MoE-Infinity (arXiv 2401.14361) [5] — sequence-level expert activation tracing, predictive prefetch + cache, 3.1–16.7x per-token latency vs offloading baselines; explicitly reports naive LRU is ineffective. Mixtral-offloading (dvmazur, LRU + speculative expert prefetch), ExpertFlow-class and DAOP/MoE-SpeQ follow-ons (arXiv 2501.10375, 2511.14102). All of these are **prefetch/caching runtimes**; none derive their win from on-disk expert *order*, and none of their mechanisms exist in llama.cpp. The honest read: in MoE offload systems the win is prediction and caching; ordering alone is ~nothing even where a reader exists.
- **Reordering for quantization quality** (the §4 prize): **RPTQ** (arXiv 2304.01089) [6] — clusters *activation* channels with similar ranges and quantizes each cluster with shared parameters, fusing the reorder into LayerNorm/adjacent weights; first workable 3-bit activations. **GPTQ act-order** (`desc_act`/`g_idx`) — processes columns in descending activation-magnitude order during error compensation; a well-established quality gain at 3–4 bit, but note it changes *quantization order*, and runtimes carry a g_idx indirection rather than a baked permutation. **AWQ** (arXiv 2306.00978) — per-channel *scaling* (not reordering) folded into the previous layer; same "fold an invariance into the checkpoint" family. **SqueezeLLM** (arXiv 2306.07629) — sensitivity-weighted non-uniform clustering of weight values. **PermuQuant** (arXiv 2605.09503, 2026) [7] — the most on-point: sorts channels by a joint weight/activation second-moment criterion *before per-group quantization* so each contiguous group shares a well-fitting scale, with a calibration-gated accept/reject; measured on diffusion models, real gains at low bits. Nothing published measures this for **GGUF k-quants specifically** — unmeasured, and cheap to measure (§4, §6).
- **Training-side clusterability** (where "cache-aware training" would earn its name): **ReLU Strikes Back** (Mirzadeh et al., arXiv 2310.04564, ICLR 2024) [8] — relufication finetune restores ~90% activation sparsity at negligible quality cost; **ProSparse** (arXiv 2402.13516) — relufication + progressive sparsity regularization (FATReLU); **TurboSparse** (arXiv 2406.05955) [9] — dReLU + data mixture, 90–97% sparsity, 2–5x decode speedup *on sparsity-exploiting runtimes* (PowerInfer); **Learn To be Efficient** (arXiv 2402.06126) [10] — trains structured/grouped co-activation so a good partition *exists*, 1.8–2.6x FLOPs reduction. All of these are real, but they are upstream of a runtime this repo does not have: training clusterability into a model whose serving engine reads every weight every token is planting a crop with no harvester.

## 4. The quantization-grouping variant

Mechanics, grounded in the actual formats. GGUF k-quants (Q4_K etc.) quantize each tensor row in **super-blocks of 256** elements along the contiguous ne[0] axis, subdivided into **8 sub-blocks of 32**, each sub-block carrying a 6-bit scale/min against fp16 super-block scales; Q4_0/Q5_0 use flat 32-element blocks with an fp16 scale each; IQ formats add codebooks. ggml's ne[0] is the matmul **input** axis. Therefore block membership — which channels must share a scale — is determined by index order along each tensor's input dimension, and the §2 algebra gives exactly two knobs that move it:

- **Per-layer MLP intermediate permutation** re-groups `ffn_down`'s blocks (input = intermediate dim). `gate/up` are affected only at whole-row granularity (their grouping is untouched). down_proj is empirically among the most quantization-sensitive tensors (llama.cpp's own quant mixes spend extra bits on it — `ffn_down` gets Q6_K in Q4_K_M for early layers), so this knob points at the right tensor.
- **Global hidden permutation** re-groups `gate/up/q/k/v` and `lm_head`/embedding blocks (input = n_embd). One permutation shared model-wide, so the objective is a compromise across all consumers; likely lower per-tensor gain than the per-layer knob, but it covers the majority of parameter bytes.
- Head permutation re-groups `attn_output` blocks at 128-element (head_dim) granularity — coarse (only head-pair membership in 256-super-blocks changes), probably marginal.

The permutation is baked into tensor data before `llama-quantize` runs: identical file size, identical bit-width, **zero llama.cpp changes**, loads as a plain GGUF. The payoff is fidelity — a Q4_K_M closer to the fp16 teacher — which matches the original "keep the existing output" constraint more directly than any technique in the first report.

**Does the gain survive k-quants' existing machinery?** Three honest deflators: (i) 32-element sub-block scales already localize range adaptation — the win from re-grouping is only the *residual* within-32-element range heterogeneity, much smaller than in the 128-group or per-tensor settings where RPTQ/GPTQ-act-order shine; (ii) the 6-bit quantized sub-scales mean grouping also interacts with scale-quantization error (grouping similar-magnitude channels makes sub-scales more uniform, which slightly *helps* here); (iii) **imatrix**: llama.cpp's importance matrix (activation second moments per input channel, collected on a calibration corpus) already weights the per-block least-squares fit so important channels get lower error *within* whatever block they land in. Imatrix does **not** change block membership — so permutation is orthogonal-and-complementary in principle (imatrix optimizes within blocks; permutation chooses the blocks), but it also means part of the naive win (protecting high-importance channels from bad scales) is already captured. The interaction to respect in implementation: the imatrix must be collected on (or permuted identically to) the permuted checkpoint, since it is indexed by input-channel position.

**Is the win real?** For per-group weight quantization in general: yes, measured — RPTQ (activations, 3-bit breakthroughs) [6], PermuQuant (diffusion weights, calibration-gated sort by second moment, gains concentrated at low bit-widths/coarse groups) [7], plus the broader channel-permutation-for-N:M-sparsity literature (PermLLM, arXiv 2510.10136). For GGUF k-quants specifically: **unmeasured, to the best of a genuine search** — no llama.cpp PR/discussion measuring permute-then-quantize for k-quants was found (nearby discussions exist for KV-cache channel permutation, e.g. llama.cpp discussion #21297). Expectation calibrated from the adjacent results: largest effect at Q4_0/IQ3/IQ4 (coarse or codebook formats), small-to-negligible at Q6_K/Q8_0; on k-quants proper, plausibly a few percent reduction in per-tensor MSE translating to a small perplexity/agreement improvement — worth one week of experiment, not worth a roadmap before the measurement. An honest possible outcome is zero-within-noise, and the experiment should be designed to report that cleanly.

Optional escalation, only if the static version shows signal: choose the permutation jointly with GPTQ-style error compensation, or add the "optional finetune to create clusterability" (a brief regularized finetune that encourages block-coherent channel statistics — the actual, narrow sense in which "cache-aware training" survives this report). Related-but-different: rotation-based incoherence processing (QuaRot arXiv 2404.00456, SpinQuant arXiv 2405.16406) folds orthogonal transforms into weights for the same fidelity goal — permutations are the zero-runtime-cost, GGUF-safe corner of that family (general rotations change activation distributions in ways some fused ops can't absorb; a permutation always folds).

## 5. Feasibility in this repo

- **A permuted GGUF is just a GGUF.** llama.cpp addresses tensors by name and shape; no mainline code assigns semantic meaning to index order along the permutable axes. Checked hazards: RoPE cares only about head_dim-internal order (untouched, §2); MoE routing consistency is preserved by permuting router rows with expert slices; `--n-cpu-moe`/`--override-tensor` operate on whole named tensors, indifferent to internal order; tensor-split/fit heuristics (Studio's own included) price bytes, not order; Metal/CUDA kernels read quant blocks positionally with no cross-row assumptions. One real constraint: do surgery in HF space *before* `convert_hf_to_gguf`, because the converter itself permutes Q/K layouts for RoPE conventions and some archs fuse tensors — reordering post-conversion invites convention bugs.
- **MoE reader check (settled in §1):** `--n-cpu-moe` is per-layer over fused expert tensors (`llama_cpp.py:4715-4747` maps Studio's count onto leading dense layers); no per-expert placement granularity exists in llama.cpp today, so expert reordering has no consumer in this repo.
- **Where the transform lives:** a standalone checkpoint transform (HF-in, HF-out) invoked before unsloth's existing export — natural home beside `unsloth/save.py`'s GGUF path (`save_pretrained_gguf` → convert → `llama-quantize`, which already threads `--imatrix` through: `save.py:366-377`). The profiling pass needs per-channel activation statistics on a calibration corpus — the **same corpus and nearly the same capture as imatrix**, which unsloth/Studio already run (Studio export: `core/export/`, `test_export_imatrix_compressed.py`). Concretely: capture second moments of down_proj inputs (act(gate) * up) per channel, combine with weight-column norms, sort or 1-D cluster into 32-element groups, emit permutation, apply to the three tensors per layer, then export as today.
- **Studio exposure:** nothing user-facing until measured. If it wins: a "quant-friendly reorder" toggle on the export screen, defaulting on for ≤4-bit exports — invisible otherwise (same file size, same load path). The fidelity harness from the first report is the gate.

## 6. How to measure

For the surviving (quantization) variant, the referee is the first report's fidelity harness — which is a concrete argument for building that harness first, since it now serves two proposals:
- Per-tensor quantization MSE / weighted-MSE (imatrix-weighted), original vs permuted, per quant type (Q4_0, Q4_K_M, IQ4_XS, Q6_K) — the mechanism-level number.
- llama.cpp `perplexity` on a held-out corpus, both files, same imatrix treatment.
- Teacher-consistency: greedy top-1 agreement and top-k KL vs the fp16 model, per context bucket — the user-visible number, and the one that decides shipping.
- Sanity: file sizes byte-identical; load and decode in the pinned llama-server.

For any future locality claim (not recommended today), measure the mechanism, not tok/s: macOS page-fault counts (`vm_stat`, `fs_usage`) and resident-set traces under `--mmap` vs `--no-mmap`; MoE offload transfer volume per token; Apple Silicon perf counters via Instruments where available. If those don't move, a tok/s delta is noise.

## 7. Verdict

Ranking by (available win) x (works with today's llama.cpp) x (effort):

1. **Quantization-grouping permutation — recommended.** Real mechanism (RPTQ/PermuQuant), unmeasured for k-quants, zero runtime changes, identical file size, lands in the existing unsloth/Studio export + imatrix path, graded by the already-proposed fidelity harness. First slice: an experiment script (permute-intermediate-dim by activation-weighted channel statistics → quantize → MSE/perplexity/agreement A-B) on one 8B model, one week, with a pre-registered kill criterion: if greedy top-1 agreement and perplexity gains are within noise at Q4_K_M *and* IQ4_XS, write down the zero and stop. Honest case against: sub-block scales + imatrix may already have eaten the win; even a real win is a fidelity epsilon, not a speedup, and only matters at ≤4-bit.
2. **MoE expert reordering — dead here, alive elsewhere.** The strongest locality case in theory, but llama.cpp has no per-expert placement or cache (fused tensors, per-layer `--n-cpu-moe`), expert slices are ~MB-contiguous already, and the systems that do win (MoE-Infinity) win on prediction/caching, not order. Only makes sense for a server/offload runtime this repo does not target — said explicitly rather than stretched to fit.
3. **mmap page-in ordering — dead for dense.** All pages are needed every token; GGUF is already execution-ordered. Nothing available.
4. **Contextual-sparsity neuron clustering — dead twice over.** No reader (mainline llama.cpp has no predict-and-skip; PowerInfer is a fork), and no sparsity in modern SiLU checkpoints without a relufication finetune; the one published clustering attempt (LLM in a flash) reports a negative result vs simple bundling. Would require adopting a PowerInfer-class runtime *and* retraining — two prerequisites, either fatal alone.
5. **Vocab reordering — dead.** Expressible but the embedding lookup is already one-row-local and lm_head is read in full; win ≈ 0.
6. **Dense decode / prefill locality — zero by arithmetic**, stated in §1; this is Studio's dominant case, which is why the locality framing of the idea does not survive contact with this repo, and the quantization framing does.

The through-line with the first report: both investigations end at the same first deliverable — the teacher-consistency fidelity harness — which is cheap, immediately useful for grading existing quants, and the precondition for honestly claiming "same outputs, cheaper" about anything.
