# Colibrì Weight-Side Optimization: Research Report

Working name: `colibri-weight-side-optimization`. Date: 2026-08-28. Third report in the series (`cache-aware-training.md`, `cache-aware-weight-layout.md`); supersedes their "no reader exists for expert-level layout" conclusion **for this runtime** — that conclusion was and remains correct for llama.cpp. Grounded in the Colibrì source at `github.com/JustVugg/colibri` (cloned and read at v1.8.0-era dev head, 2026-08-28). Status: research only, no product code.

## Summary

Colibrì is exactly the runtime the earlier reports said did not exist in this repo's path: it demand-streams individual routed experts (~19 MB coalesced `pread` per expert for GLM-5.2 int4) from disk through a per-layer LRU cache with a persistent learned pin tier, router-driven prefetch, and full miss/byte telemetry. The question "can the weights make this cache miss less?" is therefore live — but the source kills the two most literal versions of it. **Disk adjacency (pure permutation) has no consumer**: I/O is one name-addressed whole-expert read, prefetch is expert-ID-based (next layer's router run on stale state, 75.8% recall), `O_DIRECT` bypasses OS readahead, and the multi-SSD path deliberately *hash-scatters* experts across drives; at 19 MB per read, seek amortization is already done. **Static hot/cold file placement is subsumed** by the runtime's own residency machinery, which decides placement in RAM/VRAM from a persistent usage history regardless of file position. What survives, ranked by the bottleneck arithmetic (cold decode ≈ 75 layers × 8 experts × 19 MB ≈ **11.4 GB of reads per token**; tok/s ≈ disk-GB/s ÷ (11.4 × (1 − hit rate)); measured hit rates span 3–98% and map directly onto 0.07→6.8 tok/s): **(1) ship a corpus-level `.coli_usage` routing-history prior with the checkpoint** — the engine already reads exactly this file for `PIN=auto`, it is placement-only ("output unchanged" by the code's own invariant), and it removes the measured multi-run warm-up ramp (0.16→0.40 tok/s over five runs on one host); **(2) fewer bytes per expert** — quantization is a triple lever here (fewer bytes per miss, more LRU slots per GB, more pinned experts per `PIN_GB`), the engine already has int3/E8-lattice formats and a measured quality gap (per-row int4 −8.2pp, grouped scales recover ~63%), and report 2's permutation-before-grouped-quantization idea is a missing cell in Colibrì's own `quant_ablation.py`; and **(3) a router-only locality finetune** — the one intervention that changes the *access pattern* rather than the layout, for which Colibrì's opt-in `CACHE_ROUTE` (training-free, inference-time, +39% measured on one host, with `route_agree`/`route_kl` quality telemetry) is both the proof of headroom and the baseline to beat. Recommended first slice: an **offline trace-replay simulator** over Colibrì's existing `ROUTE_TRACE` stream that measures the hit-rate headroom of routing-side interventions before anyone trains anything. The honest cap: on RAM-rich hosts the profile flips to matmul/RAM-bandwidth (measured: hit 98% → disk eliminated), where none of this matters — every proposal below is for the disk-bound middle of the hardware range, which is, however, precisely the machine class Colibrì exists for.

## 1. The runtime, grounded in source

All paths below are in the Colibrì repo; `c/colibri.c` (~11.3k lines) is the GLM-5.2 engine. Blog-derived numbers from the task framing are corrected against source where they disagree.

**Model and container.** GLM-5.2: 744B MoE, **256 routed experts × 76 layers (75 main + 1 int8 MTP layer) = 19,456 experts** (README "Brain" page; benchmarks state "75 layers × 8 experts" per token) — the framing's "21,504" is not what this source says. Config is read from the checkpoint's `config.json` (`n_routed_experts`, `num_experts_per_tok`, `moe_intermediate_size`; `colibri.c:1618-1626`). The int4 container is ~370 GB on disk; the dense trunk (attention, shared experts, embeddings) is ~9.9 GB resident. MLA/DSA KV ("57× smaller KV state" per README; `glm_moe_dsa` engine id) — the framing's "~576 floats/token" is consistent with a DeepSeek-style 512+64 latent but I did not verify the exact number in code; flagged. MTP int8 head measured at 2.2–2.8 tokens/forward (issue #8). AVX2 integer-dot kernels (`IDOT`, `fused_simd.h`) at ~250 GFLOP/s claimed in `docs/benchmarks.md`.

**On-disk layout and read granularity.** Experts live in safetensors shards as pre-quantized tensors named `model.layers.<L>.mlp.experts.<E>.{gate,up,down}_proj.weight` plus `.qs` scale sidecars, located via the safetensors index (`st_find`). `expert_load_impl` (`colibri.c:2671`) sorts the three tensors by file offset and, when they are **byte-contiguous in one shard, issues ONE coalesced `pread` of ~19 MB** into a reusable slab, with the three `QT` views aliasing the slab zero-copy; non-contiguous containers fall back to three preads (`colibri.c:2610`, contiguity check at ~2862). So Colibrì has already implemented the *intra-expert* version of LLM-in-a-flash's row-column bundling, at expert granularity, in its converter+loader contract. `COLI_MMAP=1` switches to mmap views with `MADV_WILLNEED` + page-touch (the page cache becomes the cache); `DIRECT=1` uses `O_DIRECT` (default off, drive-dependent). Reads are whole-expert always; there is no sub-expert or multi-expert extent I/O.

**Cache.** Unit = one expert (per layer). `ESlot` per-layer arrays form the LRU (`ecache`, victim = smallest `used` stamp, `eslot_lru_victim`, `colibri.c:402`), with an eid→slot index for O(1) residency probes. Capacity is priced from the RAM budget per layer (`cap_for_ram`, with the #856 slab-shrink fix so MTP-width slabs don't halve the effective cap — 154→77 slots regression documented and fixed). Above the LRU sits the **pin tier**: `PIN=<usage file>` + `PIN_GB` (or `PIN=auto`) preloads the hottest experts from a persistent history; `REPIN=n` re-pins live between turns against a decaying heat map while leaving the on-disk history intact (`colibri.c:8132`). Eviction is LRU with an LFRU guard (#441/#497): a genuinely warm victim (≥2 demand accesses, 25%+hysteresis hotter than the speculative newcomer) is protected from speculative-prefetch eviction. The stats contract (`c/expert_store.h`: requests/hits/misses/prefetched/prefetch_hits/bytes_read) and per-tier hit split (`hit_pin`/`hit_ecache`, #336) already exist.

**The "learning cache".** It is the persistent routing history: `.coli_usage` in the model dir (text, sparse `layer expert count` records with engine-identity header; format contract in `docs/routing-telemetry.md` and `route_trace.h`, #700), appended every turn, read at startup by `PIN=auto`. It persists across runs — the measured "five runs later" improvement (0.16→0.40 tok/s, hit 57→71%, issue #39) is this file filling in. It is placement-only; the code asserts "Cache placement only -> output unchanged."

**Prefetch.** `PILOT=1` runs the **next layer's router on the current (stale) hidden state** and prefetches the predicted expert IDs (kind-2 lookahead, **75.8% recall** per the comment at `colibri.c:6221`; `la_hit`/`la_tot` counters). Variants: WILLNEED-hint-only, `PILOT_REAL` (actual loads into the next layer's LRU, `pilot_realload` at `colibri.c:6294`, with reservation sentinels and drop-on-conflict), `PILOT_TWO` (two-step), io_uring path (`uring.h`). Prefetch is **ID-addressed**: it predicts *which experts*, then reads them wherever they are. Nothing in the prefetch path is a sequential-extent readahead.

**Multi-SSD.** `COLI_MODEL_MIRROR` registers N model copies on N drives; `expert_route` (`colibri.c:2523`) assigns each (layer,eid) to a replica by **deterministic hash** — required so demand reads, WILLNEED hints, and page cache all agree — and `COLI_MIR_STRIPE` splits one cold expert pread into 4K-aligned chunks read from all drives in parallel (a cold 19 MB read is single-drive latency-bound at ~4 GB/s; N drives cut it ~N-fold).

**MTP and batch unions.** The MTP layer's experts are int8 (wider slabs, tracked separately via `DISK_SPLIT`). Speculative/batched forwards take the **union of routed experts across positions** in a block, loading each unique expert once; MoE-Spec (`colibri.c:1245`) optionally drops the lowest-gate-weight experts from the cross-position union to cut cold I/O. So the effective per-forward working set is the *union coherence* of routing across drafted positions — a router-behavior property, not a layout property.

**Quantization formats** (`docs/FORMATS.md`, verified against `c/quant.h`/converters): fmt=1 int8-row, fmt=2 int4-row (one f32 scale **per output row**), fmt=4 int4-grouped (scale per `gs` inputs, converter default gs=128), fmt=5 int3-g64 (3.5 bpw effective), fmt=6 E8/IQ3 lattice 256-blocks (FWHT-rotated), fmt=8 fp8 passthrough, plus an offline rANS int4 recompressor (0.76× bytes, **no engine decode path yet**). Community GLM containers exist in fmt=2 and fmt=4.

**Cache-aware routing already exists, training-free.** `CACHE_ROUTE=1` (`docs/CACHE_ROUTE.md`, default OFF) implements the max-rank strategy of *Mixture of Cache-Conditional Experts* (arXiv 2412.00099): always keep the true top-J (default 2), fill remaining slots preferring **resident** (pin ∪ LRU) experts ranked within top-M (default 12), renormalize. It *changes which experts run* and ships its own quality telemetry: `swap_pct`, `route_agree` (overlap with true top-K), `route_kl`. Measured: DGX Spark 2.4 → **3.33 tok/s** (+39%, issue #199). This is the training-free ceiling-probe for intervention (c) below.

## 2. Where the time goes

From `docs/benchmarks.md` (measured community datapoints) and source comments:

- **Cold decode ≈ 11.4 GB of expert reads per token** (75 × 8 × ~19 MB; source comment "Cold decode is disk-bound (~11 GB/token)"). The governing identity: bytes/token ≈ 600 · (1 − hit) · 19 MB, so **tok/s ≈ disk_GB/s ÷ (11.4 · (1 − hit))** until compute takes over.
- Measured hit rates and outcomes: 3–4% hit → 0.07 tok/s (24 GB WSL2 box); 23% → 1.06 (M5 Max 128 GB); 66–72% → 1.83–2.06 (M5 Max, 40–47 GB pin); **98% → 1.00 tok/s and "disk eliminated → RAM-bandwidth + matmul bound"** (EPYC, 430 GB RAM); full residency on 6×5090 → 5.8–6.8 tok/s. The cleanest controlled experiment (issue #31, same machine, disk swapped 1.5→8.8 GB/s): ×5.8 disk bandwidth bought ×2.9 tok/s and the profile **flipped from 66% disk to 57% matmul**.
- **Three regimes**, then: (i) *RAM-capacity-bound* (small RAM: the auto-cap of ~2 LRU slots/layer, not the disk, binds — "on small-RAM machines the RAM cap, not the disk, is the binding constraint"); (ii) *disk-bound* (mid RAM, the common case this report targets — M1 Ultra: 57% of decode wall is serial SSD wait at 93% of the drive's measured ceiling); (iii) *compute-bound* (big RAM / full residency — nothing weight-side below applies, Amdahl says so and the 98%-hit datapoint shows it).
- **IOPS vs bandwidth**: reads are ~19 MB each, so this is a bandwidth/latency workload, not an IOPS workload — at 4 GB/s a read takes ~4.75 ms; a random-access penalty of ~100 µs is ~2%. Physical adjacency between *different* experts is therefore worth ~nothing even before noting that no code path could exploit it.
- **Access-pattern coherence is demonstrably the big lever**: `--topp 0.7` alone (narrower sampling → more repeated routing) bought a measured 1.6× end-to-end (hit 3–4%→11%); the learned pin file bought 2.5× over five runs; CACHE_ROUTE bought +39%. All three move the *pattern*, not the layout.
- **Theoretical ceiling**: perfect cache (hit→100%) turns a 0.3 tok/s disk-bound host into its ~1–4 tok/s matmul bound — a 3–10× envelope. That envelope is what interventions (1)–(3) below compete for; nothing weight-side can exceed it.

## 3. Weight-side interventions, ranked

**(a) Pure expert-adjacency permutation on disk: dead — no consumer.** Output-preserving, yes (report 2's algebra: permute expert slices with router rows; here also trivially safe because experts are *separately named tensors* — a "permutation" is just writing them in a different file order, ids unchanged). But: the read unit is one whole expert located by name; prefetch is ID-based; `O_DIRECT` disables OS readahead; buffered mmap readahead is per-expert-extent via `MADV_WILLNEED`; the multi-SSD layer *hash-scatters* (layer,eid)→drive on purpose (determinism for cache agreement, `colibri.c:2521`); and §2's arithmetic makes inter-expert seek cost ~2%. There is no read larger than one expert and no sequential-extent predictor. The one adjacency that matters — gate/up/down + scales of the *same* expert contiguous — is already a converter contract with a measured fallback. Verdict: nothing available.

**(b) Frequency-based hot/cold placement on disk: subsumed by the runtime; the shippable version is a data file, not a layout.** Residency is decided at runtime by pin/LRU from `.coli_usage` history — file position never enters the decision. Re-clustering hot experts into one file region changes nothing the engine reads selectively (whole experts, wherever they are). What *is* real: **the history file itself is a weight-side artifact**. Today every user pays a multi-run learning ramp on every machine (measured: 0.16→0.40 tok/s across five runs, #39; "fresh history (pure LRU)" is the documented slow path). A **corpus-level `.coli_usage` prior shipped alongside the checkpoint** (computed once from diverse traffic; the format has engine-identity checks and merges with live history) gives first-run users the warmed pin set. Zero output risk (placement-only), zero engine changes (`PIN=auto` already reads it), effort ≈ running the engine over a corpus once. The project's own open-hypothesis table ("learned pins improve repeated workloads, but can overfit a prompt") says a *diverse-corpus* prior is the missing artifact. Related in spirit: the measured expert atlas (issue #175: 13,260 characterized experts, topic affinity) is exactly the profiling pass this needs.

**(c) Router-only finetune for cache locality: the highest-ceiling idea, with an honest set of caveats.** The only intervention that changes the access pattern itself. Mechanics: routers are one small matrix per layer (`mlp.gate.weight`, kept f32 by the converter — 256×hidden per layer, tens of MB total across 76 layers vs 370 GB of experts); experts stay frozen, so the *file* change is megabytes. Training signal: per-layer router inputs (hidden states) captured by running the existing engine (or the HF checkpoint on a rented node) over a corpus; loss = KL(original gate distribution ‖ new gates) + a locality term (reward temporal overlap of top-K across consecutive tokens / concentration of windowed expert mass; equivalently, differentiable-relax the LRU-hit indicator the way CACHE_ROUTE hard-codes it). Because the loss at layer L depends only on (hL, router_L), no backprop through 744B of experts is needed — **but** per-layer training on frozen traces is an approximation: once routing changes, downstream hidden states drift, so end-to-end validation is mandatory, and this is the main scientific risk. Fidelity gate: report 1's harness (top-1 agreement, KL vs the unmodified model) *plus* Colibrì's already-built `route_agree`/`route_kl`/`swap_pct` telemetry. Prior art, verified: **Mixture of Cache-Conditional Experts** (arXiv 2412.00099) — the paper Colibrì's CACHE_ROUTE implements — is *training-free* (~2× on mobile), so the trained variant is open ground; **DeepSeek-V2's device-limited routing** (arXiv 2405.04434) is the closest training-time locality constraint (top-K restricted to M devices' experts) but is from-scratch pretraining for communication, not a retrofit for an evicting cache; expert-choice routing (arXiv 2202.09368) and MoE-Infinity's finding that activation is sequence-level predictable (arXiv 2401.14361) support learnability. The honest comparison that decides whether to do it at all: CACHE_ROUTE already captures some of this win at inference time with zero training, bounded quality drift, and per-request tunability. The finetune must beat it (or compose with it: a locality-regularized router makes CACHE_ROUTE's preferred-resident fill *agree* with the true top-K more often, cutting `swap_pct` at equal hit rate — the two are complementary, not rivals). Side benefit: higher cross-token routing coherence directly shrinks the MTP batch-union (intervention (f)), multiplying the speculation win.

**(d) Working-set shrinking (expert pruning/merging, fewer experts per token): sized, and mostly declined.** Prior art exists (Not All Experts are Equal, arXiv 2402.14800; cluster-driven pruning, arXiv 2504.07807), and the engine already has the runtime knobs (`TOPK=n`, MoE-Spec union dropping, `--topp`). But pruning cold experts barely moves per-token traffic (cold experts are rarely routed — that is what cold means); its win is disk footprint, not tok/s; and it materially changes outputs on a model nobody can re-validate cheaply. Fails the preservation bar that motivated this whole series. The gentler runtime knobs already exist and are user-tunable per request.

**(e) Fewer/better bytes per expert: the strongest *works-today* lever, and where report 2's §4 lands.** On this runtime, bytes-per-expert is a **triple** lever: miss cost, LRU slots per GB (hit rate on capacity-bound hosts), and pinned experts per `PIN_GB`. Moving int4→int3-g64 (fmt=5, ~3.5/4.5 ≈ 22% fewer bytes) or E8/IQ3 (fmt=6) is already supported end-to-end by the engine; rANS int4 (0.76×) awaits an engine decode path. And the quality side is a live, measured problem: per-row int4 costs **−8.2pp** (OLMoE fp16-vs-int4 A/B, #108), grouped scales recover **~63%** of it (#225), and the repo maintains a scale-granularity/rotation/lattice ablation (`tools/quant_ablation.py`, #81) — in which **permutation-before-grouped-quantization (report 2 §4) is a missing cell**: permute the expert-FFN intermediate dim (gate/up rows + down columns, output-preserving) so similar-magnitude channels share fmt=4's gs=128 (or fmt=5's 64-wide) groups. Identical bytes, better scales, applied per expert offline. Unmeasured here as everywhere; the ablation harness to measure it already exists in-repo.

**(f) MTP/speculation: no layout angle; folds into (c).** Speculation determines *which* experts are needed (union across drafted positions); weights cannot change that except through the router. Batch-union coalescing and low-gate dropping already exist. The exploitable property is cross-position routing overlap — exactly what (c)'s temporal-coherence term trains for.

## 4. Who can apply what, to which model

- **(b') usage-prior file**: anyone with the model and a corpus; hours of inference on one machine; no checkpoint access beyond reading; **zero Colibrì code changes** (`PIN=auto` reads it today). Distribution: a file next to the shards.
- **(e) requantization / permutation-grouping**: anyone with the original fp8/bf16 checkpoint and a big disk; the converters are in-repo Python (`c/tools/convert_fp8_to_int4.py` — the permutation is ~30 lines in it); a 370 GB re-emit is an afternoon of I/O, no GPUs. No engine changes for fmt=4/5; the rANS path needs the engine-side decode PR the format doc already anticipates.
- **(c) router finetune**: needs (i) hidden-state capture — either an engine-side dump hook (small C patch) or one pass of the HF checkpoint on a rented multi-GPU node; (ii) training the routers — trivially cheap (megabytes of parameters, standard PyTorch, unsloth-irrelevant at this size); (iii) end-to-end validation on a Colibrì host. Checkpoint edit: replace `mlp.gate.weight` tensors, everything else untouched. Engine changes: none to run it; optionally a flag to A/B old-vs-new routers.
- **(a)/(d)**: (a) has nothing to apply; (d) needs pruning + re-validation infrastructure nobody in this ecosystem has for 744B.
- Nobody retrains GLM-5.2's experts; every intervention above respects that.

## 5. Measurement

Colibrì already instruments most of what a locality claim needs: per-tier hit split (`hit_pin`/`hit_ecache`), miss/byte counters (`ColiExpertStoreStats.bytes_read`, `g_prof_io`, per-drive `g_mir_bytes`), disk service time (`PROF=1`), cold/warm read classification (`DISK_SPLIT=1`, `expert_classify`), prefetch recall (`la_hit/la_tot`, pilot loads/drops), routing-quality telemetry (`route_agree`, `route_kl`, `swap_pct`), a reproducible datapoint harness (`tools/datapoint.py`, rotating-prompt median as primary), a disk microbenchmark matched to the engine's access pattern (`iobench.c`, 19 MB × N-thread reads), and quality gates (`./coli bench`, `tools/quant_ablation.py`). What is missing and would need adding: (i) an **offline cache simulator** replaying `ROUTE_TRACE` streams through the pin/LRU/PILOT policies to evaluate counterfactual routers and priors without touching the engine; (ii) a working-set-over-window metric (unique experts per N-token window, per layer) to make (c)'s target observable; (iii) for fidelity, report 1's teacher-consistency harness as the end-to-end gate on any router change (CACHE_ROUTE's `route_agree` measures *routing* agreement, not *output* agreement — both are needed).

## 6. Verdict

Ranked by (available win) × (works with Colibrì as it exists) × (effort):

1. **Ship-first: the `.coli_usage` corpus prior (b')** — small but certain: removes the measured 2.5× multi-run warm-up ramp for every new user, zero code, zero output risk. It is not the big idea; it is the free one.
2. **Biggest works-today lever: bytes per expert (e)** — fmt=5/fmt=6 containers exist end-to-end; on capacity- and disk-bound hosts a 22% byte cut compounds (miss cost × slots × pin count); and the permutation-grouping experiment from report 2 has a ready-made in-repo ablation harness plus a measured quality gap to close. Honest case against: it is a quantization project, not a cache project — the locality idea contributes only the permutation cell, which may measure zero.
3. **Highest ceiling, real risk: router-only locality finetune (c)** — the only access-pattern intervention; targets the 3–10× cold-to-compute-bound envelope; costs megabytes of trainable parameters against a 370 GB model. Risks: per-layer trace training is an approximation (hidden-state drift), quality regressions are certain-in-kind and must be gradient-bounded and harness-gated, and the training-free CACHE_ROUTE already banks part of the win (+39% measured) at zero training cost — the finetune must demonstrably beat or compose with it. **Recommended first slice, before any training: the trace-replay simulator** over existing `ROUTE_TRACE` data, reporting (i) current-policy hit rate, (ii) oracle-prefetch ceiling, (iii) CACHE_ROUTE-at-various-(J,M) frontier of hit-rate vs `route_agree`, (iv) sensitivity of hit rate to synthetic routing-coherence increases. If (iv) shows the envelope is thin, stop; if fat, train.
4. **Dead: pure adjacency permutation (a)** — no consumer in the I/O path, prefetch is ID-based, mirrors hash-scatter deliberately, seeks are 2% of a 19 MB read. The commissioner's original mental model ("reorder so a read pulls in things used together") is satisfied *within* an expert by the existing converter contract, and *across* experts by nothing, because no read crosses an expert boundary.
5. **Declined: pruning/merging (d)** — wrong side of the output-preservation constraint; its honest win (disk footprint) is not the bottleneck.

The runtime-side caveat the commissioner asked for directly: **yes, better prefetch/eviction/routing policies in Colibrì dominate most weight-side edits** — the engine's own measured history says so (CACHE_ROUTE +39%, PILOT_REAL/PILOT_TWO 1.10→1.83 tok/s on the same host, LFRU eviction guard, pin learning 2.5×), and all of those shipped without touching a single weight byte. The weight side's defensible niches are exactly the three above: a shipped prior the runtime already knows how to read, cheaper bytes the runtime already knows how to decode, and a router the runtime already treats as the model's own — each graded by telemetry that already exists and a fidelity harness this series has now justified three times over.
